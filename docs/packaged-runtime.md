# Packaged runtime — core v1

The main, `/lingxiloop`, and browser-safe `/ui` entries export the same frozen `releaseVersions`: runtime `1.0.0`, control-plane and kernel protocols `2`, initial schema `1`, LingxiLoop binding contract `1`, and committed assistant-message protocol `2`. `doctor()` and its CLI include these identifiers in `versions`. They describe this package release; they are not a negotiated compatibility handshake or proof that a consumer is compatible. Schema startup validation still checks actual tables and triggers. Release changes must update the relevant identifier explicitly; the standalone installation test compares the runtime identifier to package.json, the schema identifier to installed SQL, and the message identifier to a real packaged runtime result.

`enqueue` accepts up to 20 attachment descriptors (`id`, `sourceVersion`, `name`, `mimeType`, `size`, optional extracted `text`). Authenticated ingress must authorize the referenced source and supply its version; descriptors alone do not prove that storage bytes were verified. The package captures them with the original request and preserves them across continuation. LingxiLoop `receive` accepts `attachmentClientMsgNos` referencing committed attachments in the authorized conversation, reads each through the native bounded storage reader (16 MiB maximum), verifies its declared size and records a SHA-256 content version. Text, JSON and XML decode as UTF-8 or BOM-tagged UTF-16LE/BE; malformed encodings are rejected and the content version hashes the original bytes. DOCX text extraction uses Mammoth and PDF extraction uses PDF.js in a separate Node process, with a 10-second timeout, 128 MiB V8 heap setting, bounded output and at most two concurrent parsers per serving process. The heap setting is not an OS-level total memory cap; deployment process/container limits remain necessary. Images and formatting are explicitly excluded from extracted text. Parser overload, corruption and timeout reject ingestion. PDF extraction loads its CMaps, standard fonts and WASM from the installed dependency and disables system-font fallback; Chinese CMap extraction is covered. It preserves page numbers, limits documents to 200 pages, and explicitly marks pages without extractable text. It does not perform OCR or interpret images/layout. Other binary extraction remains pending; missing text stays explicitly unread. Continuation replies can supply additional attachments; originals and all revisions together are limited to 20 descriptors.

`app.cancel({ runId, tenantId, agentId, sessionId, threadId?, principalId })` requires an authenticated server caller and the original principal/thread. It cancels queued or waiting work immediately and signals an active lease to stop. Repeated cancellation, a different identity, and already finished non-waiting work return false. Cancellation does not undo completed business effects; the goal outcome records an inconclusive interruption, and new replies cannot resume the cancelled request.

`app.readEvents(identity, afterSeq)` returns up to 100 public events and `nextSeq` for the specified tenant, agent, session and run. Authenticate and authorize the caller before invoking this server API. Feed these events to `/ui`'s `consumeRunEvent`; internal records are excluded. A new attempt clears an uncommitted draft and waiting question, while delayed earlier events are ignored and committed messages remain intact.

The intrinsic `host.task.ask(question="...")` pauses a captured request for essential missing input. The Python cell stops at that call. `readOutcome` and public `goal.waiting` events expose the question with `awaiting_input` and its request version; no final answer is committed. Submit the reply through the continuation API below. Asking a question is not goal completion or verified business work.

The packaged app can recover a wait after a crash between a durable `task.ask` receipt and wait completion. It verifies work identity, request version and a contiguous cell receipt sequence ending in the ask, restores missing tool history and the same question, and never reexecutes Python. Missing local stdout/artifacts are explicitly marked unrecovered. Other interrupted cells still require reconciliation.

`app.continueInput({ runId, tenantId, agentId, sessionId, threadId?, principalId, inputId, requestVersion, text, attachments? })` resumes an `awaiting_input` request. Call it only from authenticated server ingress. It validates the original principal, thread and waiting version; atomically appends a request revision and requeues the same work; and deduplicates identical input IDs, text and attachments. Reply attachments stay in the new revision without replacing original attachments. Active sessions, cancelled work, stale versions and changed text under a reused input ID are rejected. The LingxiLoop `receive` entry accepts `continuation: { runId, requestVersion }`, resolving reply text and author from the committed native message instead of caller-supplied content.

The first-release package name is `lingxios`. Public exports are the root, `/worker`, `/ui`, `/eval` and `/lingxiloop`. The release scope is AgentOS/Harness core; complete LingxiLoop capability coverage is deferred by the 2026-09-06 scope decision. Registry publication is separate from the repository release and installable tarball validation.

The default app assembles PostgreSQL stores, the model driver, Python kernels, runtime and worker. It supports conversation and local Python; it grants no product actions. This is not yet the complete LingxiLoop replacement.

`createLingxiLoop` accepts optional `embeddings: { id, apiKey, baseUrl?, dimensions?, requestTimeoutMs? }`. Choose an explicit embedding model supported by the configured endpoint. Authorized memory reads backfill missing vectors through durable `memory_index` work, at most 32 records per scope per read. Local and HTTP workers process these jobs; credentials stay on the control plane. Query vectors are cached for 60 seconds with a 64-entry bound and a 3-second foreground deadline. Indexed memories are ranked by exact scoped cosine similarity, with pinned records first. Results identify semantic matches, unindexed recency, or embedding/index failures. Missing configuration keeps literal recall; outages do not prevent answering the original request. No pgvector extension is required. Index scans have a 3-second statement limit; large scopes may need an indexed vector backend before deployment. Index jobs share the three-attempt limit with synthesis; exhausted jobs require operational retry or a new memory/model version. This path has protocol tests, not live embedding-quality validation.

Python cells can call `attach_file("relative/path")` to include an existing session-home file in the current artifact output, including after a kernel restart. The runner rehashes it at cell completion using bounded reads, rejects missing or out-of-home files, and clears explicit attachments between cells. On resumed attempts the control plane supplies up to 512 prior artifact records, keeping the latest recorded entry per path, as explicitly unverified recovery context. These records do not enter the current response envelope until files are checked again; lost files are not recreated automatically.

Before committing a response, the app verifies each artifact and saves a content-addressed copy under `.committed-artifacts` in the homes root. Files are synced and linked into place without overwriting an existing copy. Later edits or deletion in the session home do not alter committed downloads. A failed message transaction may leave unreferenced copies; automatic garbage collection is not implemented.

`app.readArtifact({ runId, tenantId, agentId, sessionId, principalId, threadId? }, path)` reads only a saved artifact listed in the committed envelope. Authenticate and authorize the caller before invoking this trusted server API. It returns `{ artifact, bytes }` or `null` for unavailable identity, manifest entry or copy; changed hashes, changed sizes and directory links escaping snapshot storage are rejected. Artifact persistence and downloads above 16 MiB are not supported yet. This implementation requires access to the same persistent storage root and does not provide remote object storage.

```ts
import { createLingxiOS, doctor, packageResources } from 'lingxios'
import { pool } from './existing-database.js'

const report = await doctor({ database: pool })
if (!report.ready) throw new Error(JSON.stringify(report.checks))

const app = await createLingxiOS({
  database: pool,
  model: { apiKey: process.env.AGENT_OS_MODEL_API_KEY! },
  worker: { concurrency: 2, healthPort: 5190 },
})
await app.start()
// Invoke only after the product authenticates and authorizes this identity.
await app.enqueue({
  id: 'client-request-id', tenantId: 'tenant', agentId: 'assistant', sessionId: 'conversation',
  principalId: 'authenticated-user', text: 'Calculate 2 + 2 using Python.',
})
const message = await app.readMessage({
  runId: 'client-request-id', tenantId: 'tenant', agentId: 'assistant', sessionId: 'conversation',
})
// A null result means no final message has been committed yet.
await app.stop()
```

For an explicitly driven worker, use `runNext()` instead of `start()`. `stop()` drains then aborts remaining work after the configured grace period. The app does not close the database pool supplied by its owner.

`readOutcome(identity)` reads the goal state separately from the work lifecycle. Initial schema version 1 is required. The model submits a final JSON object with its answer, exact requirement quotes, supporting observations and remaining gaps. Only the answer body is shown to the user. The driver retains the native `ipython` function-call channel; it does not force JSON response mode on execution turns because some providers then serialize tool calls into ordinary text. This self-assessment is preserved in the envelope: `satisfied` means the model reports no unfinished requirement, not an independent proof of correctness. `verification` remains `not_run` or `inconclusive`; workers cannot self-award `passed`. Recorded resource failures, unsettled business actions or unavailable complex-content review downgrade a satisfied candidate to partial. Plain text without assessment remains partial. Simple answers require neither Python nor a separate grader call. Completion must match the durably committed assessed response, including after a worker restart. A partial candidate with remaining execution budget gets one bounded opportunity to continue available work instead of ending at a promise.

Approval waiting carries its approval ID. `delegated` requires a real pending child task in the package queue, matching the original principal, tenant, conversation, parent task and request version. Canvas assignment creation records that relationship atomically with its receipt. Unknown, cancelled, foreign and superseded task references are rejected at final submission; completion reuses the committed observation so a child finishing immediately afterwards does not break restart recovery.

Input and approval waits require matching durable `task.ask` or pending-approval receipts for the current request version. `host.task.inspect()` returns at most 64 unsettled business actions, with an explicit truncation flag; a missing receipt is unknown. The runtime repeats this inspection before final assessment, and the control plane independently rejects satisfied submissions while an action remains unsettled.

The browser-only `/ui` export provides `createRunView`, `consumeRunEvent`, `consumeAssistantMessage` and `responseSegments`. Deliver ordered events to the event consumer and only committed product messages to the message consumer. Draft text never becomes a final message merely because a run event says completed. Execution requires the triggering message to capture the original request before any model call. Delivery requires that saved request and its evidence snapshot, including an explicitly empty snapshot when there are no sources. Committed assistant messages require a response envelope; the runtime writes the outcome only there, and both the control plane and UI reject the former `data` field. Response envelopes include ordinary prose and citation annotations with source versions; annotations report support as `not_assessed`. A citation source has `truncated: true` when any cited excerpt was truncated; `responseSegments` preserves this flag for the product to display. Its absence does not establish full source coverage. Render segment text as text, never raw HTML. Product-native citation/display bindings remain pending.

## Environment and storage

The `/lingxiloop` preview accepts existing native resources directly:

```ts
import { createLingxiLoop } from 'lingxios/lingxiloop'
import * as knowledge from './modules/knowledge/public.js'
import { permissionService } from './modules/access/public.js'
import { wukongClient } from './im/wukong.js'

const app = await createLingxiLoop({ database: pool, model, services: { knowledge, permissionService, wukongClient } })
await app.receive({ companyId, agentId, channelId, clientMsgNo })

// Native calendar scheduler messages use the separately validated system ingress.
await app.receiveCalendarDispatch({ companyId, agentId, channelId, clientMsgNo })
await app.start()
```

`receive` resolves a committed native text message from the latest 100 messages and derives the principal from its author. The supported namespace methods, knowledge approvals, durable delivery recovery and teacher read scope are described below. The full first-release capability matrix remains incomplete; native streaming, teacher management and full Canvas assignment workflows are not yet available.

Set `LINGXILOOP_SOURCE` to the reference checkout’s `server/src` directory when running `npm run check:release` outside the default sibling layout. All native checks use this same path; individual commands can override it with their path argument. The reference checkout and its dependencies must exist; missing sources fail the checks.

`npm run test:contracts -- path/to/LingxiLoop/server/src` checks structural compatibility against actual native source exports without changing that checkout. This is a signature check; the executable integration test uses native-shaped fixtures, not the real domain implementation.

Node >=22.13.0 and Python >=3.10 are required. `AGENT_OS_PYTHON` or `kernel.pythonCommand` selects the interpreter. Python uses only its standard library. `packageResources()` locates the runner and SQL inside an installed package, independently of cwd.

Apply `packageResources().schema` explicitly with a database administration tool before startup. It creates only the `lingxios` schema and its Agent-owned tables. Startup and npm installation never alter storage. This is a fresh-install architecture with no data import, upgrade or dual-write paths.

`lingxios-doctor --database-module path/to/existing-pool-module.js` imports the existing module's `pool` export. Without that argument, the database check is `not_run` and readiness is false. The model check verifies configuration presence, not provider credentials or quality. Secrets are not printed.

`lingxios-worker` starts a separate worker using `AGENT_OS_CONTROL_PLANE_URL`, `AGENT_OS_SERVICE_TOKEN`, `AGENT_OS_MODEL_API_KEY`, and optional existing worker settings. The default model is `deepseek-ai/DeepSeek-V4-Flash` at `https://api.siliconflow.cn/v1`, with thinking enabled and `reasoning_effort=high`. Agent turns, structured reviews, memory processing and compaction use the same driver defaults. `AGENT_OS_MODEL`, `AGENT_OS_MODEL_BASE_URL` and `AGENT_OS_REASONING_EFFORT` are explicit overrides; reasoning effort accepts `high` or `max`. The high-level factory and evaluation reviewer accept `reasoningEffort` with the same default. The development control-plane example is not a production bootstrap.

Python audit hooks are defense in depth, not strong OS isolation. Production isolation and multi-process recovery still require deployment validation.

## Verification boundaries

### Worker container

Build the bundled remote worker with `docker build -t lingxios-worker:local .`.
The image includes Node 22, Python 3, production dependencies and packaged runtime assets.
Supply an untracked `worker.env` at runtime with `AGENT_OS_CONTROL_PLANE_URL`,
`AGENT_OS_SERVICE_TOKEN` and `AGENT_OS_MODEL_API_KEY`;
set `AGENT_OS_MODEL_BASE_URL` when using another compatible model endpoint.
Use a unique `AGENT_OS_WORKER_ID` per replica. The control plane URL must be reachable
from inside the container; container localhost is not the host machine.

```sh
docker run --rm --init --stop-timeout 30 --read-only --tmpfs /tmp:rw,noexec,nosuid,size=128m --cap-drop ALL --security-opt no-new-privileges --env-file worker.env --mount type=volume,source=lingxios-homes,target=/data/homes -p 127.0.0.1:5190:5190 lingxios-worker:local
```

The worker runs as UID/GID 1000. Existing volumes or bind mounts must be writable
by that identity. Preserve `/data/homes` across restarts and make the same homes
available to the control plane wherever its artifact operations require filesystem
access. `/healthz` checks process liveness, not model or control-plane connectivity.
SIGTERM drains active work; set the container stop timeout longer than
`AGENT_OS_SHUTDOWN_GRACE_MS` (20 seconds by default). These flags do not establish
per-agent operating-system isolation.

The image was built locally and checked as UID 1000 with a read-only root filesystem:
packaged assets were readable, Python parsed the runner, homes were writable, and
the worker polled a local protocol stub, served `/healthz`, and exited successfully
on SIGTERM. This check does not validate a deployed control plane or live model.

The PostgreSQL tests run the PostgreSQL engine through PGlite, with a test-only database-resource adapter. They cover SQL behavior and disk reopen, not concurrent networked database connections. The consumer test installs an offline tarball in a temporary directory and executes its Python runner. The app integration test uses the production HTTP model driver with a controlled local protocol server, not a live-model quality assessment.

Bind the raw `modules/canvas/index.ts` exports as `services.canvas` to enable `host.canvas.current()` for agents with the `canvas` capability. `host.canvas.available_agents()` lists native canvas-capable active agents in the tenant, after checking the human principal’s `agent:read` permission. Discovery does not enqueue work or establish delegation. `current()` reads only the current conversation after authorizing the persisted human principal; caller-supplied Canvas IDs and identity overrides are rejected. A missing canvas returns null. Use `host.canvas.create_frame(frame={type: "markdown", title: ..., content: ...})` to create a frame in the existing current canvas. The native schema validates fields; the package checks human Canvas write permission and supplies agent attribution and stable action identity. Use `host.canvas.update_frame(frameId=..., patch={baseRevision: ..., content: ...})` to edit a current-canvas frame. All changes require its observed revision and frame-level write permission; conflicts preserve the newer content. `host.canvas.append_content(frameId=..., content=...)` atomically appends at most 64 KiB of UTF-8 text within the native 1 MiB total bound. The native append has no idempotency key; uncertain execution must be reconciled against current content before another action is attempted. `host.canvas.delete_frame(frameId=...)` deletes only a frame visible in the current conversation and requires native frame write permission. Missing visibility alone is not reported as successful deletion. Reports and assignment completion are not implemented yet. `npm run test:native-canvas` runs the original native frame application and SQL in PGlite, checking stable frame creation on retry, the 1 MiB content bound, revision conflicts and denied updates. Native retries republish events; this does not establish exactly-once publication. Authorization and publication use test resources. Signature and runtime contract tests cover the binding; native report and assignment execution remain unverified.

Bind the existing `pollApplication` export from `modules/polls/index.js` as `services.pollApplication` to enable configured `polls` capabilities. The bridge supplies agent identity and stable creation idempotency, authorizes the persisted human principal, and restricts existing poll actions to the current conversation.

`npm run test:native-polls -- path/to/LingxiLoop/server/src` runs the actual reference poll domain and SQL using its existing dependencies and an isolated PGlite database. The checkout is read-only. IM publication and permission resolution use test resources; production behavior is not inferred from this check.

Bind `import * as presentations from "./modules/presentations/public.js"` as `services.presentations` to enable presentation methods for knowledge-enabled agents. Native request schemas remain authoritative. Outline approval uses the package approval continuation and rechecks the complete reviewed outline before execution. `npm run test:native-presentations` exercises native schemas and bridge arguments, not generation.

Supply `advanceAgentReadReceipt` plus the current `im/public.ts` exports to enable native chat history/send, inbox/current-room acknowledgement, search and reactions. Conversation controls add metadata, membership, topic, title and mute methods. Generic handoffs use `agents/coworker.ts`: `receiveHandoff` verifies both the created target wake and terminal completed/blocked source wake against the native record and source package action before restoring the original human principal. Clear-all unread and leaving the active execution room are intentionally not exposed.

Worker session reads use `POST /v2/work/:id/session` with the work lease and session key in the body. The bundled worker and control plane share this protocol. Local assembly uses the same lease validation.

## Recorded resource evaluation

After installation, run `lingxios-eval --observations case.json` with a JSON file such as:

```json
{
  "originalInput": "Save the complete answer in the document",
  "requestVersion": 1,
  "expectations": [{ "id": "saved", "resource": "document:1", "expected": { "body": "Complete answer", "saved": true } }],
  "observations": [{ "resource": "document:1", "requestVersion": 1, "value": { "body": "Complete answer", "saved": true } }]
}
```

Expectations must be authored from the original request; observations must come from independently reading the resource. The command scores supplied observations and does not execute the request or collect resource state. Output labels this scope explicitly. Exit codes: 0 for all resource checks passing, 1 for failure or missing coverage, 2 for invalid input. Empty checks never pass. An explicit `null` value represents observed absence; missing values do not. The input limit is 8 MiB. Reports contain input hashes and check statuses, not the original text or resource values. Semantic quality and safety coverage remain unassessed.

The `/eval` export also provides `reviewAnswer(model, { originalInput, revisions, answer, rubric })` for an independent semantic review. It preserves the original input, rejects oversized inputs instead of truncating them, and reports `not_calibrated`; it never changes runtime completion. `summarizeCalibration` compares distinct input hashes with independently human-reviewed labels, exposing disagreements, uncertain predictions and unsupported passes. `falsePassFraction` uses all samples as its denominator and includes predictions of pass against uncertain reference labels; it is not a conditional false-positive rate. Empty samples yield null rates. These helpers do not supply a human-reviewed dataset or establish live model quality.

When a turn exhausts its model-hop limit, the runtime commits an explicit partial delivery with unchecked acceptance, retaining recorded artifacts and saving execution history. It refreshes cancellation, lease and request revisions before that delivery; it does not make another model call or claim that resource changes were verified. Protocol, transport and kernel failures retain their error handling.

Recovery of an already committed response records an internal `response.recovered` event in the new lease attempt, containing the request and evidence snapshot versions. This records checkpoint reuse, not new model execution or verified goal completion. Work completion remains subject to the normal lease and request-version checks.

The LingxiLoop app exposes `inspectApproval({ companyId, userId, approvalId })` for an authenticated human review surface. It uses native approval/conversation permissions and requires the domain approval to match namespaced action intent, original authorization principal, thread and current request revisions. It returns the original request and proposed action for review; it neither approves nor executes nor resumes work. Approvals must match the single authoritative work and intent records.

Knowledge `set_source_enabled` and `delete_source` now create domain PENDING approvals and suspend the Python turn. The package records a scoped preview after native knowledge authorization and checks the durable intent, live lease and current request version when inserting it. Human approval execution uses the separate `approveKnowledge` entry point. Ordinary knowledge execution rejects these methods outside the approval path.

`rejectApproval({ companyId, userId, approvalId })` authorizes a human decision, then atomically marks the approval rejected, replaces its pending receipt with rejection, appends the decision to the preserved session, and requeues the original waiting work. Repeated rejection does not requeue again. Active sessions and mismatched request versions are refused; transaction failure rolls back the whole transition. Availability changes and business deletion support read-only postcondition reconciliation; external asset cleanup is not verified.

`approveKnowledge` authorizes the human decision, checks the source preview and expiry, and persists APPROVED plus an unknown execution receipt before invoking the native write once. Successful native results become EXECUTED receipts; thrown or unconfirmed writes require reconciliation and repeated approval never replays them. Source deletion does not claim external asset cleanup is complete. After recording execution, it atomically appends the receipt to the original session and requeues the waiting work. A failed continuation transaction preserves the execution receipt; retrying `approveKnowledge` resumes without invoking the write again. Repeated successful continuation returns `already_resumed`.

`reconcileKnowledgeApproval` reads native knowledge state without repeating a write. For approved availability changes, exactly one matching source with the requested boolean state allows continuation; absent, ambiguous or differing observations return `not_observed`. The receipt records `postcondition_observed` and `executionAttribution: not_verified`. A source missing from a list is not proof of deletion. Deletion reconciliation instead requires the tenant-scoped source deletion marker to be at or after the approval decision, checks PROJECT/private-owner visibility, and reauthorizes native knowledge reading on the source project. It reports business deletion while retaining `externalAssetCleanup: not_verified`.


`host.research.read(url=...)` also extracts PDF page text through the same isolated parser. Research downloads retain their 2 MiB bound and address/redirect checks; results include the original byte hash and a truncation flag for the 60,000-character response limit. Successful `research.read` receipts can append their returned text to the saved evidence snapshot, with stable citation markers and action-key provenance. The control plane verifies additions against the current request’s persisted read intent and result; previous evidence is immutable. Only the returned text is included, up to the snapshot’s 200-item bound. This does not assess semantic citation support or refresh old sources automatically.

`app.listenControlPlane({ serviceToken, port, host? })` starts the authenticated worker HTTP endpoint (loopback by default; port 0 selects an available port). It uses the same claim recovery as `runNext` and the local worker: delivery retries, committed-response recovery and pending-input recovery run before work is handed out. `app.stop()` closes the listener and local worker. Pass its address and token to the packaged worker's `AGENT_OS_CONTROL_PLANE_URL` and `AGENT_OS_SERVICE_TOKEN`; call `app.start()` only when also running a local worker. Artifact commitment currently requires the worker and app to use the same filesystem homes; separate hosts without shared homes are not supported by this artifact store. Omit `model` when only serving remote workers; `start` and `runNext` require it before claiming work. Local model and kernel resources are created only when local execution starts.

Teacher integration binds raw exports from the native teacher runtime/reporting/approval/management repositories, curriculum and membership applications, evaluation application, project lifecycle class and projection, identity audit and metrics. The contract check lists and verifies the exact exports. Context, reads, draft writes and approval execution use the persisted principal and current conversation/course authorization; they no longer call `loadTeacherTurnContext`, `describeTeacherAction` or `executeTeacherAction`. Native domain functions retain final authorization and business rules. Their transaction callbacks stay on the package's existing PostgreSQL connection; this requires pg-compatible query results. Registered teacher agents receive only teacher product capabilities. `current`, `overview(windowDays=1..365)`, learner/attempt/objective/activity/review/room reads and the management methods below are available. Attempt access retains native audit recording. Package tests cover these bridges and rollback; full native application authorization remains a separate release gate.

`npm run test:native-teacher` executes the unmodified native teacher reporting repository SQL for objectives, activities, pending reviews bindable rooms, learner membership, attempts and learner details in PGlite, checking tenant/project filters, joined-record isolation, room exclusions and 100-row bounds. The native room query currently returns `bound: null` for unbound rooms; the package preserves that value. It uses minimal query fixtures; the full product schema, native application authorization, overview and learner-list queries remain separate validation work. This check is included in `check:release`.

`host.teacher.draft_objectives(objectives=[...])` creates 1-100 drafts through the native teacher service inside a package transaction. Each item accepts only title, successCriteria, optional integer targetLevel (1-4) and optional prerequisiteIds (up to 100 unique IDs). Title and criteria must be non-empty and at most 10000 characters. Native project authorization and dependency checks remain authoritative. Creation does not publish objectives; uncertain creation results require inspection before retrying. Python ingress through native-shaped services, database commit and durable receipts are tested, as are unmodified native curriculum SQL and prerequisite rollback. Full native application authorization and approval-gated publication remain unverified.

`host.teacher.draft_activity(title=..., instructions=..., type=..., evaluationMode=...?, targetLevel=...?, rubric=[...]?, objectiveIds=[...]?, dueAt=...?)` creates a course activity draft in a transaction. Types are LESSON, PRACTICE, ASSESSMENT, PROJECT and REVIEW; evaluation modes are AGENT_FORMATIVE and TEACHER_REQUIRED. Text fields are required and limited to 10000 characters, targetLevel to integer 1-4, rubric and unique objective IDs to 100 items. Native defaults are TEACHER_REQUIRED and targetLevel 2. The returned resource must be a DRAFT belonging to the current course, otherwise the transaction rolls back. This does not publish the activity. Package validation, scope rollback, Python ingress through native-shaped services and durable receipts are tested. Unmodified native activity SQL also verifies scoped objective links and draft readback; full native application authorization and publication remain unverified.

`host.teacher.set_room_binding(conversationId=..., enabled=true, purpose="lab"|"discussion")` binds a group room to the current course. Unbinding requires `enabled=false` and no purpose. The enabled flag is always required and must be boolean. Execution and acknowledgement validation share a transaction. Native authorization remains authoritative; the native operation allows reassignment from another course in the same project, so callers must request that reassignment explicitly. Package parameter checks, bind/unbind and rollback on a mismatched acknowledgement are tested. Unmodified native room SQL rejects foreign tenants/projects, direct conversations and teacher rooms, and checks scoped unbinding; full native application execution remains unverified.

`host.teacher.set_learner_membership(userId=..., enabled=true|false)` manages a learner in the current course project. Explicit boolean enabled and a non-empty user ID are required; callers cannot supply a role or course scope. Execution and acknowledgement validation share a transaction. The native service requires course management permission and active company membership. Its SQL preserves existing teacher/owner roles and protects course/project creators. An acknowledgement may be a no-op for protected roles; it does not prove the user became or ceased to be a learner. Inspect native learner state before claiming the observed result. Package validation and rollback, plus unmodified native membership SQL for scope, active membership and role protection, are tested; full native application authorization remains unverified.

When native `assertTeacherApprovalFresh` is bound, the teacher capability also grants `publish_objective(objectiveId=...)`, `archive_objective(objectiveId=...)`, `publish_activity(activityId=...)` and `close_activity(activityId=...)`. These calls persist a scoped, versioned preview and suspend for human review. Application code uses `inspectApproval`, `approveTeacher` or `rejectApproval` with `{companyId,userId,approvalId}`. Approval locks the waiting work and native target, rechecks the original teacher identity and preview, executes with the transaction client, verifies the target status and commits the receipt atomically. Successful execution then resumes the task; retrying recovery does not execute again. The Python publication path through native-shaped services and rollback/stale-preview checks pass. Full native application authorization and concurrency testing remain separate checks. review_evaluation(evaluationId=..., decision="accept"|"reject", reason=...) uses the same approval flow and verifies ACCEPTED or REJECTED after native execution. The reason is required and limited to 10000 characters. Native learning-state projection and attempt updates remain inside the native transaction; their full application behavior is not established by the package acknowledgement checks. Teacher membership approval is additionally granted when requireLearningCourseRole, setLearningCourseMembershipRecord and enqueueLearningEffect are bound to their native exports. set_teacher_membership(userId=..., enabled=true|false) checks the native teacher role, applies the protected native membership change and queues teacher_room.sync in the same transaction as the approval receipt. `transition_course(command="END"|"ENTER_READ_ONLY"|"ARCHIVE")` uses the same version-bound human approval path.
